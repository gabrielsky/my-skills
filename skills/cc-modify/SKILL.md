# cc-modify

按用户为本技能设定的顺序处理修改。先识别被改对象代表的业务概念，沿关联关系查清影响，再给用户看具体方案，确认后执行。用户已明确确认过同一份具体方案时，直接按已确认范围执行。

## 1. 说明这次改变了什么

只读检查原需求、用户最新指示、实际实现和交付状态。用一句话说明被改对象代表什么概念，这次要纠正或改变什么，以业务语义、现有契约和可观察行为为依据。

区分名称纠正、业务含义变化、职责调整和结构调整。例如将“订单”明确为“订阅订单”，先查清原来就只处理订阅订单，还是本次要缩小处理范围。前者主要影响表达，后者还可能影响筛选条件、校验和调用方。

## 2. 沿概念追踪关联对象

从被改对象的定义和引用出发，沿创建、调用、转换、存储和消费关系，找到同一概念在系统中的其他表达。遵循项目规定的代码检索方式。旧名称、缩写和同义词可作为检索线索，继续用实际关系确认关联性。

根据本次变化选择相关方向，检查已存在的对象。

| 关联方向 | 需要检查的对象 | 判断重点 |
|---|---|---|
| 各层表示 | Domain、Entity、DAO、Repository、Service、DTO、Command | 是否表达同一业务对象，名称与职责是否一致 |
| 创建和使用 | Factory、Loader、调用方、方法、参数、变量、集合 | 是否仍在按旧含义创建或使用对象 |
| 数据转换与存储 | Mapper、Converter、字段、表、SQL、序列化 | 含义、单位、取值范围和映射是否需要同步 |
| 行为与生命周期 | 状态、事件、监听器、定时任务、补偿任务 | 触发条件、动作和结果是否受影响，名称是否仍准确 |
| 对外契约 | API、消息、配置及其消费者 | 消费方依赖什么，历史数据和已有部署如何兼容 |
| 验证与说明 | 测试名称、数据和断言、文档、示例、提交、MR 或 PR | 是否准确表达修改后的行为和完整交付物 |

有相关提交、MR 或 PR 时，分别读取提交主题与正文、MR 或 PR 标题与正文。标题和正文可能处于不同状态，逐项核对。

## 3. 判断是否需要联动

对查到的关联对象，依据实际职责和契约决定如何处理。

- 同一业务概念的专属对象，检查其名称、字段、方法和行为是否应同步调整。
- 承担更广职责或表达不同概念的对象，按它自身的业务含义判断，说明保留现有表达的理由。
- 表名、JSON 字段、消息类型、配置键等可被外部依赖的名称，先查消费者与历史数据，再提出兼容或迁移方案。内部类型改名与外部契约调整分别列明。
- 若发现一个对象混合多个业务概念，先说明职责问题及其与当前目标的关系，再决定是否需要拆分或调整。

追踪到关联对象的名称、职责和契约仍然成立时，可在该方向停止。只把完成本次目标所需的修改纳入方案，其他问题单独记录。

## 4. 把方案交给用户确认

用简短方案列出以下内容。小修改可以用几行说明。

1. **目标与依据**。说明概念或行为如何变化，以及判断依据。
2. **需要联动修改**。点名具体对象、关联原因和改法。命名和说明直接给出新文案。
3. **检查后保留**。对容易被认为应一起修改、但实际职责或含义不同的对象，说明理由。
4. **需要用户决定**。列出契约兼容、历史数据、职责拆分或范围扩大的选择。超出用户明确限定范围的修改单独作为可选项。
5. **验证与交付**。说明如何验证行为和命名的一致性。查清分支、提交是否已推送、MR 或 PR 是否仍开放，明确追加提交、改写历史、推送和编辑远端说明等动作。

用可用的提问工具请用户确认方案。没有提问工具时，在回复中给出方案并等待下一轮确认。确认前只做只读调查和方案准备，等待用户回复后再改文件、提交、推送或编辑远端。原始修改请求、赶时间和改动很小都不能代替方案确认。

## 5. 执行并核对

按确认范围完成修改。发现需要改变业务行为、扩大范围或增加远端操作时，先把新增部分交给用户确认。

交付前逐项核对方案与最终差异。按风险执行适当验证，再检查保留下来的旧名称、注释、测试描述和配置是否仍准确表达业务含义。编译通过能验证引用是否合法，概念表达的一致性需要另外核对。

涉及提交和 MR 或 PR 时，读取实际提交和远端状态，核实已确认的主题、标题和正文都已同步。报告完成项、验证结果和仍待处理的已知差异。

## 示例

将领域对象 `Order` 明确为 `SubscriptionOrder` 时，检查专门存取它的 `OrderRepository`、`OrderDao` 以及相关 Entity、DTO、转换器和测试是否需要同步改名。查明 `OrderService` 是否专门处理订阅订单。若 `PaymentService` 负责多种订单的支付，按其通用职责保留名称。已有数据库表和消息字段需结合消费者、历史数据单独决定。把这些判断与对应的提交、MR 文案调整一起交给用户确认。
