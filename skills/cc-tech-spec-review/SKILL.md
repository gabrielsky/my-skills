# tech-spec-review

审一份 markdown 技术文档。两种子类型：

- **spec 规范/约定**：编码规范、分层约定、命名约定、建表/迁移规范、测试规范……一条条"代码该怎么写"的规则。品质单元 = **规则**。
- **arch 架构设计**：模块职责、边界、数据流、技术选型……一个个设计决策。品质单元 = **决策**。

## 北极星（唯一判据）

这类文档的目的是**指导新代码怎么写**。所以每条 finding 都要能落到下面任一句，落不到就别记：

1. **会让新代码写错** —— 规则/决策技术上有问题，照着写出 bug / 性能 / 一致性事故（最高价值）。
2. **会让新代码写歧义** —— 规则糊、矛盾、强制度不清，两个人理解不同、写出不一致的代码。
3. **新代码没指引** —— 该有的规则/边界缺失，这块全靠各自发挥。
4. **找不到该守的规则** —— 规则太多没归类，读者翻不到相关那条。

**你是专家，不是文字编辑**：不止挑文档毛病，要对技术内容给**自己的改进建议**——尤其揪出被写成钦定规范的反模式（照着写整个团队都写错）。

## 与邻居 skill 的分工

- 审**产品需求**（功能/UI/验收）→ [cc-prd-review]，不是这里。
- **术语**单维对齐代码 → [cc-terminology]。
- 审**代码本身**是否遵守了规范 → 那是 code review / 静态检查的事。本 skill **不读代码取证**：技术文档指导的是未来代码，不是描述存量，跟存量比对没意义。文档若下了现状断言（"现有都这么写"）→ 标"未核实"，不展开。

## 接受输入 / 触发

- 单个 markdown 文件路径（推荐 `dev-docs/*.md`、模块 `CLAUDE.md`）或贴在对话里的全文。无路径无内容则反问。
- **仅手动触发**。非 markdown / 非中文也照做，但提醒一次。

## 工作流

0. **判子类型**。通篇在立"必须/禁止/应当"的可执行规则 → spec；通篇在描述模块/组件/数据流/选型决策 → arch；都有 → 混合（两套都过）。判不出（更像产品需求）→ 反问或转 [cc-prd-review]。

1. **通读 + 抓"指导哪块新代码"**。一句话写清：这份文档想规范/设计的是**哪个范围的新代码**（命名？分层？建表？某子系统设计？）。这是后面判"完备/盲区"的范围基准。**不要边读边写报告**——容易漏全局矛盾（前文一条规则后文示例又违反它）。

2. **拆单元 + 金字塔聚类**。spec → 把每条规则拆成原子条目 `{id=R#, 强制度, 断言}`；arch → 拆成 `{id=A#, 决策, 结论}`。**id 顺序给定后永不变**，强制度只做字段。**规则/决策多时**（> ~8 条）边拆边按主题聚成金字塔类目（顶层主题 → 子规则），类目**从文档自身的规则主题自然聚出**，不外部硬塞。聚类规则见 `references/gap-and-consistency.md`。

3. **过六引擎**。逐条目过 Q/G/C/T/E/D 六维，配合 references 打勾。命中即记 finding。
   - **Q 品质** —— 每条规则/决策成不成立（写得清不清）。详 `references/rule-quality.md`（规则）/ `references/decision-quality.md`（决策）。
   - **G 完备/盲区** —— 只从文档自身推内部盲区。详 `references/gap-and-consistency.md`。
   - **C 自洽** —— 内部矛盾。详 `references/gap-and-consistency.md`。
   - **T 分类** —— 规则多时是否 MECE 归类、每组小结论先行。详 `references/gap-and-consistency.md`。
   - **E 技术专业性** —— 以领域专家眼审技术内容：有没有把反模式写成规范？决策技术上成不成立、有没有更优解？详 `references/tech-expertise.md`。
   - **D 冗余/单源** —— 同一规则/定义是否重复多处、该收口到单一权威源（防漂移成矛盾）。详 `references/gap-and-consistency.md`。

4. **排严重度**。P0/P1/P2（见下），按北极星：写错 > 找不到 > 读着累。

5. **写改进建议**。每条 finding 给原文摘录 + 改写后版本（diff 思路即可）。E 类不只说"不对"，要给**更优的写法/设计**。手法见 `references/rewrite-patterns.md`。

6. **汇总**。明确判断：这份文档现在**能不能拿去指导新代码** / 还缺什么才能用。

7. **复审收口**（改写采纳后才走，见下）。

## 编号约定（5 个命名空间，互不复用）

一个概念一个前缀；**会变的属性（严重度 / 强制度）做字段，绝不焊进 id**——否则复审一 rebucket（P1→P0、规则改强制度），所有交叉引用全失链。

| 命名空间 | 写法 | 说明 |
|---|---|---|
| 引擎（6 维） | `Q` 品质 · `G` 完备 · `C` 自洽 · `T` 分类 · `E` 专业性 · `D` 冗余 | finding 与正文**一律用字母**，不再另设序号 |
| 引擎内 checklist 项 | 规则品质 `Q1-Q5` · 决策品质 `Qd1-Qd4` | 见 `rule-quality.md` / `decision-quality.md` |
| 文档规则单元 | `R1 R2 R3…` 顺序号 | 强制度 `[MUST]/[SHOULD]/[MAY]` 做 chip，**不进 id** |
| 文档决策单元 | `A1 A2…`（ADR） | |
| finding | `[F01] [F02]…` 顺序号 | 严重度 `P0/P1/P2` 做字段，**不进 id**；id 一旦给定永不变 |

上表 5 个命名空间按**符号形状**一眼可分（形状与命名空间正交，仅助肉眼定位）：引擎/检查项字母 `Q/Qd/G/C/T/E/D`（`Q1-Q5`/`Qd1-Qd4` 是 `Q` 引擎的嵌套检查项，非独立前缀）· 文档单元 `R#/A#` · finding `[F#]`。严重度 `P#`、强制度 `[MUST]` 是正交字段（非命名空间），不计入命名空间数。引用进**被审文档**时（`位置` 字段）优先用文档自带的小节锚 / 规则原号 + ≤40 字摘录，别只写自由文本，否则复审 diff 对不上。

## 六引擎（详见 references，此处列维度名 + 核心问，防两处展开漂移）

### Q 品质（每条规则/决策成不成立）

- 规则：**可判定**（"必须 X" vs "尽量优雅"）· **有 WHY**（防什么坑）· **有反例**（只正例易误读）· **强制度分级**（MUST/SHOULD/MAY）· **主语+范围+前提**（谁/何时/什么场景适用、边界）。
- 决策（ADR 测）：**背景**（解决什么问题）· **备选+取舍**（为什么选它不选别的）· **代价/边界**（已知代价、适用边界）· **影响**（牵动哪些模块/约束）。

### G 完备 / 内部盲区（只从文档自身推，不引外部"应该有"清单）

开放枚举（"A、B 等"的"等"、状态列了没列全转移、列正常没列异常）· 悬空引用（引了术语/规则号/模块文档自己没定义）· 单边规则（定了"怎么进"没定"怎么出/撤销/回滚"）· 前提无边界（"X 时这样"没说"非 X 怎么办"）· 决策半截（给方案没给代价）· 存量策略缺（新规上线存量怎么办没说）。

### C 自洽（内部矛盾，也只看文档）

前后规则冲突 · **示例违反自身规则（示例自打脸）** · 同概念多名混用 · 默认值与校验冲突。

### T 分类（规则/决策多时）

规则是否 MECE 归类（不重叠不遗漏）· 每组是否**小结论先行**（首句说清本组管什么）· 有没有规则归错组 / 一条规则横跨两组 / 几十条铺平无分组。**注意**：这是给一堆**原子规则**归类，不是 PRD 那种整篇章节排序重排——别动文档整体章节顺序。

### E 技术专业性（domain expert lens —— 本 skill 最高价值）

拿 Java/Kotlin/Spring/DDD/MySQL/Redis 专家知识，审**文档里白纸黑字写的那条规则 / 那个决策 / 那段示例代码**技术上对不对、好不好。

**审的是文档，不是代码库**：你的全部输入就是这份文档的文字。**绝不打开仓库去查"谁违反了这条规则"**——那是别人**拿这份文档**去做的下游 code review，不是本 skill 的活。本 skill 只判这把尺子本身刻得对不对。

- **文档把反模式写成了规范？**（文档里那条 MUST / 那段示例本身就是反模式：让用字段注入、把贫血模型当 DDD、cache-aside 没带空值防护、复合索引列序写反…）
- **文档里的决策技术上成不成立？** 有没有更优解、性能 / 一致性 / 并发陷阱？
- **给更好的写法/设计**，不只挑错——直接改文档里那条规则 / 那段示例。
- **边界**：纯技术对错大胆判；依赖业务背景的取舍 → 标"需结合业务确认"。

### D 冗余 / 单源（同一规则/定义是否重复多处）

同一规则 / 定义 / 约束在文档里**重复出现多处**，没收口到单一权威源。落北极星「写歧义 + 找不到」：多副本无权威源 → 改一处漏其余 → **漂移成矛盾（未来 C 类 P0）**，读者也不知信哪份。**是「防 C 于未发」**——C 抓已矛盾的，D 抓还没矛盾但迟早漂的重复源。形态（规则正文复述 / 多表同源 / 约束散点 / 声明复述 / **冗余引用陈述**——引用裹复述、违职责单一）、收口修法、**误杀边界（纯指针交叉引用 ≠ 重复，但引用裹复述要报；总览+展开 ≠ 重复）**详 `references/gap-and-consistency.md`。

### 引擎归属裁定（防重叠与重复刷数量）

一个问题常同时沾两个引擎。按下表钉死主归属，**选一个主引擎记 finding，其余在 `引擎` 字段附注**（如 `E 主 / G 附`），禁止同一问题拆成两条：

| 灰色地带 | 归哪 |
|---|---|
| 规则编号断号 / 重号 | **Q1**（规则自身没写清），不归 C |
| 决策给了方案没给代价/边界 | **Qd3**（arch 决策品质） |
| 规则方向对、但漏技术防护/配套（缓存没空值、发事件没一致性、读 dao 没只读事务） | **E**（见 tech-expertise "防护半截"），不算 G |
| 该有的规则/分支**整条缺失** | **G** 完备 |
| 图与正文 / 前后规则 / 示例与规则 互相打架 | **C** 自洽 |
| 规则没归类 / 归错组 | **T** 分类 |
| 规则 id 拿**强制度**当前缀（`MUST-01`）或**全局流水跨类目递增** | **T**（id 该 = 金字塔一级类目 + 类内递增，强制度退回 chip），区别于 Q1 断号/重号是现状错 |
| 同一规则/定义被**重抄**多处、当前副本还一致 | **D** 冗余（防 C 于未发），不是 C |
| 多副本**已漂移**成互相矛盾 | **C** 自洽，不是 D |
| 同一概念用了**多个不同名字** | **C**（同概念多名混用），不是 D（D 是同内容多处） |
| 规则重复**只因没归类**散落各组 | **T** 分类；整段约束被重抄则 **D** |

## 严重度（按"读者照着写新代码会怎样"定）

- **P0 误导 / 卡死 / 坏代码**：
  - 自相矛盾、示例违反自身规则（C）
  - 规则糊到没法照做、决策无依据无法落地（Q）
  - 关键分支盲区让人卡住（G）
  - 规则归错组导致误用（T）
  - **把反模式写成钦定规范 / 技术错误的决策——照着写新代码必出 bug / 性能 / 一致性事故（E）**
- **P1 摩擦**：缺 WHY / 缺反例 / 强制度不分（Q）· 缺存量策略 / 枚举不闭合 / 决策没说代价（G）· 分类乱 / 无分组找不到（T）· 次优方案 / 有更优实践没用上 / 陷阱没提示（E）· **整段实质约束被重抄多处、各处独立维护、迟早漂移成矛盾（D）**。读者会反复回来问。
- **P2 打磨**：表达 / 编号 / 措辞 / 纯风格偏好 · 短的导航性重述（D，读着累不漂移）。不影响照做。

**结论判定**（写报告头，勿凭感觉）：任一 P0 → **关键处先修才能指导新代码**；无 P0 但 P1 ≥ 3 → **建议补充后再用**；否则 → **可指导新代码**。

## 复审收口（改写采纳后重审）

**触发**：(1) 本 skill 自己改完源文件后自动走一轮；(2) 用户手动把建议并入文档后说"再审 / 复审"。

**做什么**：

1. 拿**更新后的文档**（有上一版报告就 diff 对照，没有就让用户给原报告或重抓 findings）。
2. **逐条核对原 findings 的状态**：✅ 真解决 / ⚠️ 改了但没解决 / ❌ 改出新问题。"改了"不等于"解决"——核实是否真消除了北极星层面的危害。
3. **C 自洽、T 分类 全局重扫**，不只看改动处。局部修一条规则可能跟别处冲突、或打乱原有归类——这是改写最常见的副作用。
4. **E 技术专业性复核**改动处：新写法 / 新决策本身是不是好实践，别按下葫芦起了瓢。
5. 出**复审结论**：全部收口 / 残留 N 条 / 新引入 M 条 → 需要就再来一轮，循环到干净或用户喊停。

**原则**：不重复已收口的条目；只报**状态变化 + 新问题**。别把复审写成从零再来一遍的长报告。复审轮次的报告末尾加一张收口表：

````markdown
## 复审收口（复审轮次出）
| 原 finding | 原严重度 | 状态 | 说明 |
|---|---|---|---|
| [F01] | P0 | ✅ 收口 | 反模式已改为构造器注入 |
| [F03] | P1 | ⚠️ 未解决 | 补了反例但仍无 WHY |
| [F09]（新增）| P0 | ❌ 新引入 | 改写后 §3.2 与 §5.1 出现新矛盾 |

**结论**：残留 1 + 新增 1，建议再修一轮。
````

## 改写交付（用户确认后才动源文件）

默认只出报告。当用户**调用时明确说"直接改 / 出报告并改"**，或**看完报告后确认采纳**：

1. 按 P0 → P1 顺序改源文件，每改一处在对应 finding 标"✅ 已改"。P2 默认不改，除非点名。
2. **最小改动**：保留作者原有语气、术语、章节风格。
3. E 专家建议落地时，把更优写法/反例实际写进文档（不是只在报告里说）。
4. arch 文档涉及架构图 → **同步更新 Mermaid**，别文字改了图没改。
5. 改完给 **diff 摘要**，并**自动走一轮复审收口**（见上）确认真改对、没起新问题。
6. 不确定的（依赖业务/技术决策本身）→ 不擅自改，留报告里标"待作者确认"。

## 写报告时的注意事项

- **每条 finding 先过北极星**：问自己"这会让新代码 写错/写歧义/没指引/找不到 吗"，落不到就删。防刷数量。
- **引原文准确**。复制原文不意译，超 40 字截前 40 加省略号。**规则写在表格里时引"表名 + 列名/行 + 单元格关键词"**。
- **位置可定位**。优先引文档自带的小节锚 / 规则原号，配 ≤40 字原文摘录做二次定位（复审 diff 才对得上）；退而求其次才用章节名 / 表格列 / 代码块。
- **一个 finding 只讲一件事**。
- **改写要落地**。说"建议明确"是废话；直接给"明确成什么样"。E 类直接给更优代码/设计。
- **不发明事实**。没写明的背景写"未指明 / 待确认"，别替作者假设。
- **保持中文语境**。技术词允许英文（Spring、DDD、SLA、CQRS）。

## 何时反问

- 子类型判不出、更像产品需求 → 先问或转 [cc-prd-review]。
- 早期草稿大纲（< 50 行）→ 问"是否要按六引擎补全"，直接审意义不大。
- 只贴片段问"这段怎么样" → 只评这段，别越界审整篇。
- 同时给多份 → 问优先级，一份一份来。

## 不做的事

- **不读代码取证**（不翻代码查文档与存量是否一致——文档指导的是新代码）。现状断言标"未核实"。
- **不擅自改源文件**（除非确认，见「改写交付」）。
- **不做整篇章节重排 / 迁移表**（金字塔只用于规则归类，不搬迁文档整体结构）。但 **D 冗余的纯去重式合并允许**：收口重复规则到一处 + 引 ID、合并列重叠的表、重复声明上提——这些只删重复、不改规则的逻辑归属与章节顺序，区别于 PRD 式整篇重排。
- 涉及**依赖业务背景**的取舍 → 引用原文 + 标"需结合业务确认"，不硬判。纯技术层面则大胆给建议（这是核心价值）。
