# 架构决策品质 cheatsheet（引擎 Q，arch 类；checklist 项 Qd1-Qd4）

逐个决策打勾。每项「核心问（绑北极星：照着设计/扩展能不能做对）+ 反例 + 怎么改」。命中即 finding。

一份好架构文档 = 一串可追溯的决策（ADR 风格）。不是"我们现在长这样"的快照，而是"为什么是这样、怎么扩"。

---

## Qd1 背景（解决什么问题）

**核心问**：这个决策要解的是哪个具体问题？没背景的决策，后人不知道前提变了能不能推翻它。

- [ ] 每个非平凡决策有一句"为了解决 X"？
- [ ] 背景里的约束（团队/技术栈/时间/数据量级）写了？

**反例**：
> 会话缓存用 Redis。

→ 为什么需要缓存？解决什么？后人不敢动也不知道何时该动。

**改**：
> 会话上下文需跨实例共享、读多写多、可容忍过期淘汰 → 用 Redis 缓存（背景：单会话上下文 ~10KB，峰值 500 QPS）。

---

## Qd2 备选 + 取舍（为什么选它不选别的）

**核心问**：考虑过哪些方案、为什么选中这个？只甩结论的决策无法评判对错，也教不会读者"遇到类似问题怎么权衡"。

- [ ] 列了 ≥1 个被放弃的备选 + 放弃理由？
- [ ] 选中理由是具体权衡，不是"业界都这么用"？

**反例**：
> 消息队列选 RocketMQ。

→ 没说和 Kafka / RabbitMQ 比什么、为什么。读者无法判断这决策稳不稳、自己新场景该不该照搬。

**改**：
> 选 RocketMQ：需要事务消息 + 顺序消息（订单状态变更），Kafka 顺序需单分区牺牲吞吐、事务消息弱；RabbitMQ 吞吐不够。代价：运维多一套中间件。

---

## Qd3 代价 / 边界（已知代价、适用边界）

**核心问**：这决策的代价是什么、什么场景不适用？不写代价 = 读者把局部最优当银弹到处套。

- [ ] 写了已知代价 / 引入的复杂度 / 新依赖？
- [ ] 划了适用边界（什么场景用、什么场景别用）？

**反例**：
> 统一用 CompletableFuture 做异步编排，提升吞吐。

→ 没说代价：异常处理变复杂、线程池打满风险、调试困难；也没说哪些场景不该异步（强一致、短链路）。新人到处套，写出难维护代码。

**改**：补代价+边界
> 高扇出 I/O 密集链路用 CompletableFuture 编排；代价：异常需显式 `exceptionally` 兜底、共用线程池需隔离；**不适用**：强一致事务内、单步短链路（直接同步更清晰）。

---

## Qd4 影响（牵动哪些模块 / 约束）

**核心问**：这决策约束了哪些模块、给下游加了什么前提？照着扩展的人要知道边界在哪。

- [ ] 说了影响范围（哪些模块要配合、哪些接口要遵守）？
- [ ] 扩展点明确（新增一类怎么接，而不是改核心）？
- [ ] 模块职责单一、依赖方向单向（文档自述层面，不取证）？

**反例**：
> 各平台差异在 PlatformService 里按 platformType 分别处理。

→ 没有扩展点，加平台要改核心 switch。新人照着写 = 开闭原则破坏，每加一个平台改一处核心。

**改**：
> 平台差异收敛到 `PlatformAdapter` 接口；新增平台 = 实现一个 Adapter 并注册，核心流程零改动。现有 tb/dd 各一实现。

## arch 文档常见品质问题（也归 Q，但偏写法）

- **空话形容词当指标**：'高性能/高可用/高并发' 无数字 → 等于没约束，读者不知道按什么量级设计。改为 P95<2s / 99.9% / 500 QPS。（同 rule-quality Q1 不可判定）
- **快照而非决策**：通篇"系统由 A、B、C 组成"，零个"为什么"。→ 这是说明书不是设计文档，无法指导新代码做同类决策。
- **图文内部矛盾** → 归 C 自洽（不是这）。
- **技术选型本身就错 / 有更优解** → 归 E 技术专业性（不是这；Qd1-Qd4 只管"决策讲清没讲清"，不管"选得对不对"）。

---

## 与其他引擎的边界

- 决策**技术上选错了 / 有明显更优解** → E 技术专业性。
- 该有的决策**整个缺失**（如没说失败降级）→ G 完备/盲区（但只在文档已半截提及时记；不外部硬塞"必须有降级章节"）。
- 图与正文 / 图与图**互相矛盾** → C 自洽。
