# 技术专业性嗅觉清单（引擎 E）

你是 **Java/Kotlin/Spring/DDD/MySQL/Redis 资深专家**。这一引擎不审"文档写得清不清"，审"**文档里写的技术内容对不对、好不好**"。最高价值：**揪出被写成钦定规范的反模式**——一条坏规则会让整个团队照着写错。

> ⚠️ **审的是文档，不是代码库。** 下面这些反模式，是拿来比对**文档里写的规则、示例代码、决策**的尺子：若文档把某条写成了规范、或它给的示例代码本身就踩了坑 → 记 finding。**绝不要打开代码仓库去查"谁违反了这些"**——那是别人拿这份文档做 code review 的下游事，不属本 skill。你需要的全部输入就是这份文档的文字。各条目里的"规范让…/被写成规范/示例…"都指**文档文本**，不是去仓库找实例。

**这不是穷举清单**，是唤醒嗅觉的高信号样本。读文档时凭专家经验主动找更多。每条反模式 → 给**更优写法/设计**，不只说"不对"。
**边界**：纯技术对错 → 大胆判 + 给建议；依赖业务背景的取舍 → 标"需结合业务确认"。

## 两类命中（都要抓）

1. **钦定反模式**：把坏东西写成 MUST/推荐（字段注入、贫血模型当 DDD…）→ 团队集体写错 → 常 **P0**。
2. **防护半截**：规则**主方向对、但漏了配套防护/边界** → 照着写出"对了一半"的代码 → 常 **P1**。**在高质量文档里这类比纯反模式多得多**，最易被放过：
   - cache-aside 写了，没写**空值缓存 / 互斥重建 / 过期打散**（穿透/击穿/雪崩）
   - "落库后发 MQ 事件"写了，没写**落库与发消息的一致性**（事务消息/本地消息表/outbox）
   - "QueryAppService 直读 dao 无事务"写了，多读一致性场景没说**只读事务**
   - "加分布式锁"写了，没写**过期 / 持有者校验 / 续期**
   下面各域条目里凡"没说 X / 无防护"的，都属这类——别因为规则看着对就放过，揪出缺的那半截。

## Java / 通用

- **可变共享状态没说线程安全**：规范让 new 个 `SimpleDateFormat` / `HashMap` 当字段共享 → 非线程安全。→ `DateTimeFormatter`（不可变）/ 明确并发容器。
- **异常吞掉**：示例 `catch (Exception e) {}` 或 `catch` 后只 log 不处理被当常态 → 吞错。→ 要么恢复要么抛，日志带上下文。
- **用异常做控制流** / 返回 null 当正常分支 → 调用方易 NPE。→ `Optional` 或空对象，且文档说清。
- **equals/hashCode、可变对象做 Map key** 没提约束 → 隐蔽 bug。
- **基础类型装箱、字符串拼接 SQL/日志在热点路径** 被默认 → 性能/注入。

## Kotlin

- **`data class` 带 `var` / 可变集合**当领域对象 → 不变量被绕过。→ `val` + 不可变集合，变更走 `copy()`。
- **平台类型（Java 互操作）没标可空性** → 运行期 NPE。→ 边界显式 `?`/`!!` 策略。
- **`!!` 当常规手段** 写进规范 → 等于关掉空安全。→ 只在真不可能为空处用，否则 `?:`/`requireNotNull`。
- **`companion object` 放可变状态** → 伪单例共享态。
- 滥用扩展函数 / `apply`-`run`-`let` 嵌套到不可读当推荐风格。

## Spring

- **字段注入 `@Autowired`/`@Resource` 当推荐** → 难测、隐藏依赖、循环依赖晚发现。→ **构造器注入**（本项目栈应钦定这个，反之是反模式）。
- **`@Transactional` 自调用失效**没提：同类内 this 调用 `@Transactional` 方法事务不生效——规范若让"Service 内部方法标 @Transactional 互相调用"必踩坑。→ 说清代理机制 + 事务方法跨 bean 调或自注入。
- **`@Transactional` 范围套了远程调用 / 长 I/O** → 连接占用、长事务。→ 事务只裹 DB 操作，外部调用挪出。
- **`@Transactional(readOnly=false)` 默认 + 大批量** 无分批 → 长事务锁。
- **`@Async` / 线程池用默认 SimpleAsyncTaskExecutor**（每次新线程）被默认 → 资源耗尽。→ 明确有界线程池 + 拒绝策略。
- **`@Cacheable` 没说 key 设计 / 失效 / 空值穿透** → 缓存问题全留给实现者。
- 在 `@PostConstruct` 里做重 I/O、循环依赖靠 `@Lazy` 硬解当推荐。

## DDD

- **贫血模型当 DDD**：实体只有 getter/setter，逻辑全在 Service → 不是 DDD，是事务脚本。→ 行为/不变量进领域对象（呼应本项目 [[feedback_ddd_naming]] Bo+DmService）。
- **聚合边界过大**：一个聚合塞进一堆实体，一次加载/锁全量 → 性能与并发差。→ 聚合按不变量边界划小，跨聚合用 ID 引用 + 最终一致。
- **领域层依赖基础设施 / Spring 注解渗进领域对象** → 领域不纯、难测。→ 领域只依赖 Port 接口（呼应 DmService 只依赖 Port）。
- **领域服务 vs 应用服务职责混淆**：把编排（事务、跨聚合）写进领域服务，或把业务规则写进 AppService。
- **仓储返回可变集合 / 暴露 ORM 实体到领域外**。

## MySQL

- **索引最左前缀踩空**：规范给的复合索引顺序与高频查询条件不匹配 / 范围列放中间断了后续列 → 索引用不上。
- **隐式类型转换废索引**：字段 `varchar` 用数字查、函数包列 `WHERE date(col)=` → 全表扫。→ 类型对齐、避免列上套函数。
- **大事务 / 大批量单条提交** 被默认 → 主从延迟、锁等待。→ 分批。
- **`SELECT *`、无分页深翻 `LIMIT 100000,20`、外键级联** 写进规范当常态。
- **字符集/排序规则没定**（utf8 vs utf8mb4） → emoji 截断、隐式转换。（本项目有 mysql-guidelines，可呼应而非重复）
- **唯一约束 vs 逻辑删除冲突**：软删 + 唯一索引没处理，删了不能重建同名。
- **用 `NOW()`/随机 在被复制语句** 影响一致性。

## Redis

- **大 key / 大 value**（一个 key 存整个列表/大 hash）被默认 → 阻塞、迁移难。→ 拆分、控制元素数。
- **缓存击穿/穿透/雪崩无防护**：规范让"查不到查库回填"但没说**空值缓存 / 互斥重建 / 过期打散** → 热点失效瞬间打垮库。
- **`KEYS *` / 无 `SCAN`、`HGETALL` 大 hash、阻塞命令在主线程** 当常规。
- **缓存与库一致性策略含糊**：先写库还是先删缓存？延迟双删？规范不说 → 各写各的、脏读。→ 明确 cache-aside + 失效时机。
- **分布式锁用 `SETNX` 没设过期 / 没校验持有者 / 没续期** → 死锁或误删他人锁。→ Redlock/Redisson 语义说清。
- **把 Redis 当数据库**（强一致/持久化关键数据只放 Redis）当设计。
