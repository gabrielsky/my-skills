# 规则品质 cheatsheet（引擎 Q，spec 类；checklist 项 Q1-Q5）

逐条规则打勾。每项「核心问（绑北极星：能不能照着把新代码写对）+ 反例 + 怎么改」。命中即 finding。

---

## Q1 可判定

**核心问**：这条能在 PR / code review 里判出"遵守了 / 违反了"吗？不能判定 = 等于没规则，每人尺度不同，新代码必然不一致。

- [ ] "必须 / 禁止 / 应当 X" 可判真假，不是"尽量 / 适当 / 优雅 / 合理"？
- [ ] 判据客观（数字、具体符号、可枚举），不靠主观感觉？
- [ ] 没有"视情况而定 / 酌情"这种把判断权全甩给读者的条款？
- [ ] 规则编号连续无断号、无重号（断号让人疑漏抄、引用对不上）？

**反例**：
> 类应保持职责单一，方法不宜过长，命名要优雅。

→ "不宜过长"多长？"优雅"谁定？三个 reviewer 三个尺度。

**改**：
> 单方法 ≤ 60 行（超出拆私有方法）；类公开方法 ≤ 15 个；命名遵循 [命名表]，禁拼音、单字母（循环计数器除外）。

---

## Q2 有 WHY（防什么坑）

**核心问**：写了这条防的是什么坑？没 WHY 的规则会被当教条，遇到不适用的场景照样硬套，或干脆绕过。

- [ ] 每条非平凡规则有一句"为什么"（防哪个具体问题 / 哪次事故）？
- [ ] WHY 让读者能自己判断"我这个场景算不算例外"？

**反例**：
> 禁止在 Service 里直接 new 领域对象。

→ 为什么？读者不知道，要么盲从、要么觉得多此一举绕过。

**改**：
> 禁止在 Service 里直接 `new` 领域对象——领域对象的不变量应由工厂/聚合根保证，直接 new 会绕过校验造出非法状态。

---

## Q3 有反例

**核心问**：给了"❌ 错误写法"吗？只有正例的规范，读者照抄正例但绕不开自己那个变体的坑。

- [ ] 每条非平凡规则配 ✅ 正例 + ❌ 反例？
- [ ] 反例标"错在哪"，不只甩段代码？
- [ ] 易误读的边界给了"这种情况算违反吗"？

**反例**：
> 跨模块只能调对方 Provider。
> ```java
> userProvider.findById(id); // ✅
> ```

→ 只有正例。读者不知道"AppService 直接注对方 DAO 算不算违反"。

**改**：补 ❌
> ```java
> @Resource UserDao userDao;     // ❌ 跨模块直接注对方 DAO
> @Resource UserTxService svc;   // ❌ 跨模块摸对方事务层
> ```

---

## Q4 强制度分级

**核心问**：哪些必须、哪些可破例，读者分得清吗？全是"建议"= 全员当耳旁风。

- [ ] 文档显眼处声明 MUST / SHOULD / MAY（必须/应当/可以）的含义？
- [ ] 每条标了强制度，不混在一起让人猜？
- [ ] SHOULD 类说了"什么情况可破例 + 怎么记录"？

**反例**：
> 建议用不可变对象。建议返回 Optional 而非 null。建议……

→ 全"建议"，读者不知哪条硬线哪条偏好，最后全忽略。

**改**：
> - [MUST] 对外返回集合禁止返回 null，用空集合。
> - [SHOULD] 值对象用不可变；确需可变在类注释说明理由。
> - [MAY] 简单 DTO 可用 record。

---

## Q5 主语 + 范围 + 前提

**核心问**：谁执行、何时、什么场景适用、边界在哪？缺了这些，读者不知道自己这段新代码该不该套这条。

- [ ] 规则主语明确（谁来做 / 谁来校验）？
- [ ] 适用范围清楚（新代码 / 存量 / 哪个模块 / 哪层）？
- [ ] 前提条件给了边界（"X 时这样"配套"非 X 怎么办"）？
- [ ] 存量怎么办说了（一刀切会让存量全飘红）？

**反例**：
> 所有查询必须走缓存。

→ 哪种查询？强一致场景也走？缓存没命中怎么办？存量直查的要不要改？无法照做。

**改**：
> [MUST] 高频只读、可容忍秒级陈旧的查询走缓存（cache-aside）；强一致场景（如库存扣减）禁止走缓存，直查主库。存量不主动改，新代码遵守。

---

## 与其他引擎的边界

- 规则**示例违反规则自身** → 归 C 自洽（示例自打脸），不在这。
- 规则**技术上就是错的 / 是反模式** → 归 E 技术专业性，不在这（Q1-Q5 只管"写得清不清"，不管"对不对"）。
- 该有的规则**整条缺失** → 归 G 完备/盲区。
