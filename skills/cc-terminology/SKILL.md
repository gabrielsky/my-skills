# terminology

中文技术文档/PRD 的**术语治理**。文档可读性的地基是术语：一个概念一个词、对齐代码字段、对立概念名字呼应。本 skill 把这套工程化。

四种能力，按用户意图选其一（也可串起来：先建表 → 查错 → 改写）：

| 能力 | 触发语 | 产出 | 是否改源文件 |
|------|--------|------|------------|
| **建表** | "建术语表""抽术语""整理词表" | `术语\|直觉锚\|含义\|代码标识` 表 | 否（除非要求嵌入） |
| **查错** | "术语有没有问题""用词一致吗""这几个词是不是一个意思" | P0/P1/P2 诊断报告 | 否 |
| **改写** | "统一术语""按术语表改""把 X 都改成 Y" | 改写后的文档 | **是，先确认** |
| **维护** | "校验是否遵守术语表""补新术语" | 违规清单 + 增量表项 | 仅术语表增量 |

模式判不准时反问一次。下面先讲贯穿全模式的术语表格式与原则，再讲各模式工作流。

## 术语表格式（钦定）

沿用本仓库 PRD 既有约定（见 `docs/淘宝AI客服-实时应答.md` §0.1），不要另造格式：

```markdown
| 术语 | 直觉锚 | 含义 | 代码标识 |
|------|--------|------|---------|
| **候选 Agent** | candidate · "竞争上岗的客服 Agent" | 一次请求中参与竞争应答的 Agent；最多选 1 个作答 | `AgentMiddleResult` |
| **会话焦点**（简称焦点） | session-focus · "整通对话主聊的商品/订单" | 会话级，对接方传 | `focus_item_info` |
| **句内提及**（简称提及） | mention · "买家这句随手贴的商品" | 消息级，siren 从卡片解析 | `mentioned_item_infos` |
```

四列各自的职责：

- **术语**：钦定的唯一用词，全文一致。常用简称在括号里标（`（简称焦点）`），简称也算钦定词。加粗。
- **直觉锚**：`英文 · "大白话"`。让人不查表也能猜个八九分。**仅抽象的中文术语需要**——"环境变量""候选淘汰"这类要给；"订单""价格"这种一看就懂的不用硬凑。
- **含义**：一句话边界。说不清边界 = 这个概念本身没想清，回头找作者澄清，别糊。
- **代码标识**：对应的类名/字段名/枚举值，`反引号`。没有就 `—`。这列是文档↔代码的可追溯锚点，最值钱。

两条额外手法（来自本仓库 PRD，值得延续）：
- **对立概念名字刻意呼应**：`会话焦点 ↔ 句内提及`（整通 vs 这一句）、`预填 ↔ 后填`（对接方填 vs siren 填）。成对的概念用成对的词，读者一看名字就知道二者关系。
- **代码标识仅首次出现注明**：正文里一个术语第一次出现时挂一次代码标识即可，后文不重复挂。

## 识别术语 + 正文标记

抽术语、查错前先得能判"正文这个词到底是不是术语"，以及"够格的术语在正文里标了没"。

**判定信号**（命中即当术语）：

1. **反复出现 + 承载业务语义**——多处出现、指一个特定对象/动作。「候选 Agent」「会话焦点」是；「这个」「然后」不是。
2. **能锚到代码字段**——背后对得上类名/字段/枚举。对得上 → 几乎一定是术语。
3. **有明确边界、可定义**——一句话能说清是什么/不是什么。
4. **换个词读者会以为是别的东西**——不可随意替换。「焦点」换「主商品」让人懵 → 是术语。
5. **对接/研发要照它干活**——影响理解或实现的词。

**反信号**（不是术语，别硬列）：日常通用词、能用"已有术语+限定"说清的、全文只出现一次的。

**正文标记规范**（让读者一眼认出"这是钦定术语，查表有定义"）：

- **首次出现加粗**：`**会话焦点**`。
- **首次出现挂代码标识**：`会话焦点（focus_item_info）`，后文不重复挂。
- **链回术语表**：全文开头有 `## 术语表`，正文加粗词都能回表查。
- 后文只用钦定词、保持一致；不再重复加粗/挂标识。

查错与维护模式据此挑出"够格当术语但正文没加粗/没挂标识/没入表"的词。

## 术语原则

判定术语好坏、找问题的依据。详见 `references/principles.md`，速记十条：

1. **唯一性**——一个概念一个词。别"用户/客户/会员"混指同一对象。
2. **一致性**——全文同一写法。"下单/提交订单/创建订单"别混。
3. **无歧义**——一词只一义。"状态"太泛 → "订单状态"/"支付状态"。
4. **可定义**——每个术语一句话能划清边界。划不清 = 概念没想清。
5. **区分性**——相近概念用明显不同的词。"取消/关闭/退款"要分得开；对立概念名字呼应。
6. **业务对齐**——用业务方真实说法，别拿工程黑话当产品术语。
7. **显式优先**——缩写、代号首次出现给全称/定义。
8. **命名映射**——文档术语 ↔ 代码字段 ↔ UI 文案 三者可追溯（即"代码标识"列存在的理由）。
9. **稳定性**——术语定了别随意改；要改全局改并记录。
10. **粒度恰当**——不过度细分（增认知负担），不过度笼统（生歧义）。

## 各模式工作流

### 建表

1. **划范围**。确认要覆盖哪些文档/代码目录。一篇 PRD → 就这篇；"整理项目术语" → 问清目录。
2. **抽概念**。通读目标，捞出反复出现、且承载业务语义的名词。**优先派 Explore 子 agent** 去对应代码仓库核实每个概念的真实代码标识（类名/字段/枚举），别凭文档猜——文档里的中文词常和代码字段对不上，这正是要锚定的。子 agent 只读不改、返回 `中文概念 → 代码标识` 映射。
3. **去重**。把指同一对象的不同写法合并成一项（这一步就是在执行原则 1/2）。合并时记下"被废弃的同义写法"，改写模式要用。
4. **填表**。按上面四列填。抽象中文词补直觉锚，对立概念检查名字是否呼应、不呼应就改名。
5. **产出**。默认输出独立 markdown 表，问用户是否嵌入目标文档的 `## 术语表` 章节（PRD 习惯放在最前，§0.x）。

### 查错

不改文件，输出诊断报告。

1. **读全文 + 列概念清单**。先整篇吃进去，列出文中所有承载语义的名词及其各处写法。**不要边读边记**——容易漏跨段矛盾（前文"允许重名"后文"唯一性校验"这种）。
2. **核实现状（条件触发）**。若文中出现"复用 XX""系统已有 YY""与现有 ZZ 一致"这类断言、且当前在对应代码仓库内：派 Explore 子 agent 核实被引用的术语/字段是否真存在、文档当作"新概念"的是不是系统早有既定叫法。不在仓库/纯文本则跳过，并在报告头标注"未核实代码现状"。
3. **逐条过十原则**。每个概念对照 §术语原则十条扫一遍，命中即记 finding。重点抓：同概念多写法（违 1/2）、一词多义（违 3）、相近概念撞名（违 5）、文档词与代码字段对不上（违 8）。
4. **按严重度排序**：
   - **P0**——会导致研发/对接理解错（一词多义、文档词与代码字段冲突、对立概念名字混淆）。
   - **P1**——同概念多写法、缩写未定义、边界说不清。
   - **P2**——直觉锚缺失、粒度可优化等体验问题。
5. **每条 finding 给**：原文摘录（标位置）+ 问题（违反哪条原则）+ 建议钦定词。末尾汇总该文档术语是否达到"可进研发评审"。

### 改写

**改源文件，先确认再动手。**

1. **要有术语表**。没有就先跑建表模式产出表 + "废弃同义写法 → 钦定词"映射，让用户确认。
2. **列改动清单**。扫目标文档，逐处列出"非标写法 → 钦定词 + 行号"。**先给清单让用户过一眼**，别闷头全改——有些"同义写法"在特定上下文其实是另一个概念（如"状态"有时确实泛指），机械替换会错。
3. **确认后改**。用精确替换，保留代码块、引用、表格结构不动。改完报告改了多少处。
4. **不碰代码标识**。`反引号` 里的类名/字段是代码真实标识，永远不改。

### 维护

1. **拿现有术语表**。定位文档里已有的 `## 术语表` 或独立词表。
2. **校验遵守**。扫正文，凡用了表外同义写法、或违反表中钦定词的，列违规清单（复用查错模式的 P0/P1/P2）。
3. **增量补**。正文出现了表里没有、但承载语义的新概念，按四列格式补成增量表项，问用户是否并入。
4. **不擅自改既有表项**。改动稳定术语会牵动全文（原则 9），只提建议，由用户拍板。

## 边界

- 只管中文技术文档/PRD 的术语。代码内部命名规范走 `java-coding-standards` 等专门 skill。
- 与 cc-prd-review 的关系：cc-prd-review 是整篇全维度审、仅手动；本 skill 单术语维度、可自动触发。用户在做 PRD 全面 review 时让 cc-prd-review 主导，术语细节可调用本 skill。
- 改写模式动源文件前必须确认，这是不可逆操作。
