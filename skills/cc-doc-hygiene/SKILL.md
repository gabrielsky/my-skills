# doc-hygiene

改完 markdown 后的文字自查。只管**文字卫生**，不管内容对错——规则对不对是 `cc-tech-spec-review`，需求全不全是 `cc-prd-review`。

## 输入

- 默认 `git diff`（含未提交改动），四类全查。
- 文件路径：只查 B、C、D。A 类需要"删前"版本，无 diff 时跳过，在输出末尾注明"A 类未检查（无 diff）"。终稿里"封闭语义 + 否定重列"的句子可标为疑似 A1。
- 想查历史改动：先 `git diff <base>..HEAD -- <file>`，把结果作为输入。

## A. 删除没删干净

根因一个：不敢真删，怕丢信息。于是删除被降级成"改写"或"留框架"。

**A1 否定式残留**——删掉的项换成否定句留在原地。

> 原文：只能吃鸡、鸭、鱼、肉、白菜、豆腐
> 要求：改成只能吃鸡、鸭、鱼
> AI 产出：只能吃鸡、鸭、鱼，~~不要吃肉、白菜、豆腐~~

前半句已是封闭语义（只能 / 仅 / 必须 / 一律 / 唯一 / 全部 / 有且只有），后半句又用否定重列被排除项 —— 后半句删。

**判别**（否定句不能一刀切删）：不写这半句，读者会做错吗？

- 不会 → 冗余型，删。前半句已经排除它了。
- 会 → 防错型，留。否定项是读者的默认反射或常见错法（"用 rebase 不用 merge"——merge 才是肌肉记忆）。

同型变体：`不再支持 X`（把已删的历史留在规范里，规范只写现在该怎么做）、`而非 X` / `不是 X` 对照句、`X 时触发；Y、Z 时不触发`（触发条件已穷举就别补反面）。

**A2 空壳**——内容删了，架子还立着。逐项对着 diff 查：

- 引导句：删了三条只剩一条，上面还写着"需要注意以下几点"
- 计数：正文"三个阶段"，实际剩两个 —— 按 D 处理，改数字不如删数字
- 交叉引用 / 锚点：指向已删小节
- 目录、汇总表、末尾清单里的已删条目
- 只剩标题没有内容的小节

## B. 口播

书面文档不是讲稿。整句删，不是改写：

接下来我们来看 / 首先…其次…最后（当过渡句用，当编号用没问题）/ 综上所述 / 总的来说 / 值得注意的是 / 需要指出的是 / 大家可以看到 / 希望本文能帮助 / 以上就是……的全部内容 / 让我们一起

## C. 冗余

- 同一条规则文档里出现两次 —— 留信息最全那处，另一处改成链接
- 先概述、再详述、最后总结的三段式 —— 只留详述
- 解释比规则本身长 —— 规则自明就别解释；真需要解释就写 why（为什么这么定），不写 what 的复述

## D. 会过时的计数

文档里写死的数量，代码一改就错，而且没人回来改。删数字，留描述。

- 现：报表类都在 `service/` 下（当前 6 个类）
- 改：报表类都在 `service/` 下

**判别**：这个数字变了，读者会做错吗？

- 不会 → 删。数字只是顺手补的，读者真要准确数量会去数代码。
- 会 → 改写成约束，不是快照。"最多重试 3 次"是规则，"目前有 3 个实现"是快照。

同型：文件行数、"共 12 个接口"、"目前支持 A/B/C 三种"（枚举留着，"三种"删）、版本号清单、覆盖率百分比。

## 输出

逐条，不写报告体：

```
路径:行  [A1|A2|B|C|D]
- 现：<原文>
- 改：<改后；整句删就写"删">
```

无发现就一句"干净"。本 skill 自己的输出也守 B、C。
