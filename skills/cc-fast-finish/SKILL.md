# 快速收尾

用户显式调用 `/cc-fast-finish`，表示要求执行当前任务的提交、合并回主干、推送及当前 worktree 清理，而不是只给出命令建议。按顺序完成，不重复询问是否执行已经明确授权的步骤；工具权限审批及环境限制仍然有效。遇到下述停止条件时保留现场并报告，不强行继续。

## 1. 确认范围与状态

- 阅读当前仓库的 `CLAUDE.md`、`AGENTS.md` 等适用指令，遵守测试、提交格式及署名约定。
- 用 `git status --short`、`git diff`、`git diff --cached`、`git branch --show-current`、`git remote -v` 和 `git worktree list --porcelain` 确认当前工作目录、任务分支、远端、主干所在 worktree，记录绝对路径。
- 优先从远端默认分支及仓库约定确定主干，不把会话的任意基准分支当作主干，不硬编码远端名称或 `master`/`main`；不能确认时停止，不猜测。
- detached HEAD、正在进行 merge/rebase/cherry-pick、存在未解决冲突、无法确定改动归属时停止。
- 只处理当前任务分支及其 worktree，不碰其他任务的 worktree，不把无关改动或敏感文件加入提交。
- 先说明将要操作的分支、推送目标和准备清理的路径。创建 Skill 本身不等于调用本 Skill。

## 2. 检查并提交当前任务

- 查看包括未跟踪文件在内的待提交内容，按仓库约定运行与改动有关的测试或构建。纯文档/Skill 改动检查内容、格式及 `git diff --check`，不必启动应用。
- 测试失败或必要验证无法运行时停止，报告原因，不继续合并和推送。
- 用明确的文件路径暂存属于当前任务的改动，检查暂存差异后生成准确的提交信息并提交。不要盲目执行 `git add .` 或 `git add -A`。
- 没有待提交改动时跳过提交，继续检查分支上已有的任务提交。没有实际变更时不创建空提交。
- 记录任务提交 SHA，并确认工作区干净；若还有不属于当前任务的未提交内容，保留它们并停止收尾。

## 3. 同步并合并主干

- Fetch 目标远端，确认远端主干的最新状态，并检查任务分支相对远端主干的全部提交及差异；发现无关提交时停止。
- 需要把最新主干合入当前任务分支时：在桌面应用创建的 worktree 中，使用应用的 `sync_with_base_branch` 工具，显式指定已确认的主干；其他环境使用正常 Git 合并。该操作只是更新任务分支，不代表已合并回主干。
- 冲突时停止并报告冲突文件，不自动选择 ours/theirs，不使用 reset 或强制覆盖。
- 在主干所在的干净 worktree 中执行主干更新和最终合并。若主干没有被任何 worktree 检出，可在权限允许的位置创建临时集成 worktree；不要切换其他任务 worktree 的分支。
- 访问主干目录仍受当前会话的目录权限及工作目录限制约束；被限制或被拒绝时停止，不用其他工具、子代理或会话绕过。
- 确认主干 worktree 没有已暂存、未暂存或未跟踪的用户改动。检查本地主干与远端主干的关系：本地主干落后时仅允许 fast-forward；存在尚未推送且不属于当前任务的本地提交，或双方分叉时停止，避免顺带发布其他工作。
- 将任务分支以完整引用 `refs/heads/<任务分支>` 合入主干。能够 fast-forward 时优先使用 `git merge --ff-only`；否则使用正常 merge，保留历史，不自动 squash 或 rebase。
- 根据合并后的实际差异运行必要验证，确认成功后再推送。若合并产生新的提交，遵守仓库提交及署名约定。
- 若调用时已在主干上，只提交并推送明确属于当前任务的内容，跳过合并，绝不删除主干工作目录。

## 4. 推送并核实

- 只推送确认过的主干引用，使用明确的 refspec：`git push <远端> refs/heads/<主干>:refs/heads/<主干>`，不使用隐式目标、不推送所有分支。
- 不使用 `--force` 或 `--force-with-lease`，不绕过 hooks、分支保护或权限要求。
- 若远端拒绝推送（包括主干在此期间被更新），停止并保留本地提交及 worktree。报告实际错误，不谎称已完成。
- 推送成功后，用 `git ls-remote <远端> refs/heads/<主干>` 核实远端 SHA。若远端又有新提交，fetch 后通过祖先关系确认本次主干提交仍被包含。
- 同时确认任务提交已经包含在所推送的主干历史中。未确认发布成功前，绝不清理 worktree。

## 5. 清理当前任务 worktree

- 只清理此次调用开始时记录的任务 worktree，以及此次流程自行创建且已不需要的临时集成 worktree；不清理主仓库、主干 worktree 或其他会话的目录。
- 删除前再次检查路径、分支、HEAD、工作区、未跟踪及忽略文件（包括 `git status --short --untracked-files=all --ignored`）。有未提交内容或需保留的忽略文件时停止清理；不能确认忽略文件是可丢弃的构建产物时也保留目录。
- 停止本次会话自己启动且仍占用该 worktree 的进程，不终止其他会话或用户的进程。
- 使用环境提供的 worktree 生命周期工具（若适用）退出并清理；工具只管理特定来源的 worktree 时，不假定它能删除其他来源的目录。
- 普通 Git worktree 在权限允许时，从不会被删除的目录使用 `git worktree remove <准确路径>`。如果环境无法安全离开当前 worktree，保留目录并报告清理受阻，不删除正在使用的当前工作目录。
- 不使用 `git worktree remove --force`、`rm -rf`、`git clean -fd` 或 `git reset --hard`。不使用共享 stash 存放现场。
- 不删除远端任务分支；保留本地任务分支，除非生命周期工具的正常清理同时删除它或用户另行要求删除。
- 清理后通过 `git worktree list` 核实结果。工具的 no-op 不算清理成功。若环境规定退出后不能继续操作，先完成所有可执行的核实，再退出并如实说明核实范围。

## 结果报告

简洁报告：任务提交 SHA、主干及推送远端、验证结果、远端发布核实结果、worktree 是否已清理。任何一步失败，明确已完成到哪里、保留了哪些提交和目录、未完成的原因；不要将部分完成描述为全部完成。
