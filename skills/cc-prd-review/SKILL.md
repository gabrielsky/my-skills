# prd-review

审阅一份中文 markdown PRD，输出**诊断报告 + 改写建议**。不直接覆盖源文件。用户决定是否采纳后再改。

## 接受输入

- 单个 markdown 文件路径（推荐 `product-doc/prd/*.md`）
- 也接受贴在对话里的 PRD 全文

无路径无内容则反问。非 markdown / 非中文 PRD 也照做，但提醒一次。

## 工作流

0. **判 PRD 类型**。先确定是普通功能 PRD 还是"数据契约"性质（统一业务模型 / 开放平台 API / 跨系统对接协议）。无法从标题/正文判断时反问用户一次。此判断决定维度 3 字段审查深度（普通 PRD 不查类型/长度，数据契约 PRD 全查）。
1. **完整读一遍 + 抓核心意图**。先把全文吃进去。读完一句话写清：**本 PRD 要做/改什么功能**、**声称复用或依赖哪些现有模块**、**引用了哪些现有术语/状态/表**。这三项是下一步核实的清单。**不要边读边写报告** —— 容易漏全局矛盾（如前文"允许重名"后文又"唯一性校验"）。
2. **核实现状（条件触发，防无效建议）**。若 step 1 清单里出现"复用 XX 模块 / 系统已有 YY / 与现有 ZZ 一致"这类对现状的断言，**且当前在对应代码仓库内**：派一个 Explore 子 agent 去核实，再回来审。核实点：① 被复用的模块/类是否真存在、复用边界实际情况；② PRD 当作新术语要求定义的，是否其实系统早有既定概念（有则不该提"未定义"）；③ PRD 描述的状态机/字段是否与现有实现冲突。子 agent 只读不改，返回结论不返回大段代码。**不满足条件**（无仓库 / 纯文本 PRD / 全新功能无现状）则跳过，并在报告头标注"未核实代码现状，复用与术语类建议仅基于 PRD 文本，请 PM 自行核对"。
3. **画出 PRD 现有结构骨架**。把现有章节列成树状目录，标注每章在做什么（业务规则 / UI 交互 / 横切关注点 / 混杂）。这一步专门暴露结构问题。判骨架时读 `references/structure-template.md` 的"章节归属判定规则"。
4. **按维度过一遍**。逐项扫下列 12 个维度（0 结构合规 + 1-11 内容质量）。配合 `references/dimensions-cheatsheet.md` 逐项打勾。**带着 step 2 的现状结论审** —— 现状已澄清的点不再记 finding。任何一处命中即记为 finding。
5. **按严重度排序**。P0/P1/P2 三档（见下），P0 在前。
6. **写改写建议**。对每个 finding 给出原文摘录 + 改写后版本，diff 思路即可，不必整段重写。改写手法参考 `references/rewrite-patterns.md`。
7. **给结构重组建议**。如有结构问题，在报告末尾附"建议目录骨架"，按 `references/structure-template.md` 的金字塔模板（业务/UI 拆分 + 横切独立）重排现有章节。
8. **末尾汇总**。给出"是否阻塞研发评审 / 联调"的明确判断。

## PRD 结构规范（金字塔原则）

好 PRD 自上而下层层展开，结论先行，每层 MECE（不重不漏）。**业务规则、UI 交互、横切关注点必须分离**，否则研发难以并行（后端只看业务规则，前端只看 UI 交互，运维/数据只看横切）。

标准目录骨架（**顶级 6 章按重要程度递减排列**；相关章节聚合为子章节；顶级中文序号，子级数字序号）：

```
一、需求概述                ← Why + Who + 场景。读这个就能 80% 理解需求
   1.1 业务背景与痛点（含量化数据）
   1.2 目标与非目标
   1.3 成功指标
   1.4 角色定义
   1.5 核心用例 / 用户故事（含流程图）

二、业务规则                ← 核心 What。系统怎么算 / 怎么转移 / 怎么校验
   2.1 术语表
   2.2 业务字段（仅业务语义）
   2.3 状态机（状态、转移、并发策略）
   2.4 业务校验与计算（编规则 ID）
   2.5 边界与异常（数量上限、空态、降级、迁移）
   2.6 与其他模块的依赖与复用边界

三、UI 交互                 ← 用户感知层。引用 二、业务规则
   3.1 入口与信息架构
   3.2 页面布局（列表 / 创建编辑 / 详情 / 弹窗）
   3.3 控件清单（控件类型、placeholder、默认值显示、错误文案）
   3.4 交互流（操作路径、灰显规则、二次确认）
   3.5 各种态展示（空 / 加载 / 错误 / 越权）

四、运营与治理              ← 横切聚合：上线后运营 / 安全 / 数据看的
   4.1 操作日志（记录动作清单、日志字段、不记录项、展示位置）
   4.2 权限（角色矩阵、隔离策略、越权拦截）
   4.3 统计分析与埋点（业务指标、埋点事件、数据看板入口）

五、技术对接                ← 跨团队联调锚点
   5.1 与算法侧 / 风控侧 / 第三方 的同步时机与协议
   5.2 入参 / 出参 / 错误码 / 超时 / 重试 / 失败兜底
   5.3 SLA 与容量约定

六、验收与上线              ← QA + 运维锚点
   6.1 验收用例（每条可测）
   6.2 性能 / 容量 SLA
   6.3 灰度与回滚方案
   6.4 兼容性与数据迁移
```

**章节组织三原则**（用来判断现有 PRD 是否合规）：

1. **按重要程度排序**：先答 Why（一），再答 What 业务（二）/ What 表现（三），最后答辅助层（四 / 五 / 六）。读者一路读下来认知负担最低。颠倒顺序（如把数据迁移放最前）即为 finding。
2. **相关聚合，不要散**：
   - 操作日志 / 权限 / 统计埋点 同属"治理"语义，合为「四、运营与治理」三个子节，而不是三个独立顶级章节。
   - 背景 / 目标 / 用户 / 用例 同属"需求是什么"，合为「一、需求概述」五个子节。
   - 顶级章节超过 6 个就要质疑：能不能合？
3. **同层 MECE，不越界**：业务规则不写 UI 控件；UI 不重定业务校验，引用规则 ID。

**序号规则**（强制）：

- 顶级 H2 中文序号：`## 一、需求概述`、`## 二、业务规则` …
- 子级 H3 数字：`### 1.1`、`### 1.2` …
- 三级 H4 数字递进：`#### 1.1.1`
- 跨章引用：顶级用中文（`见 四、运营与治理`），子级用数字（`见 2.4`）
- 顶级超过十时用「十、十一」；但通常 6 章足够，超 8 章基本是聚合不够

**金字塔的核心要求**：
- **结论先行**：每章首段一句话说清"本章做什么 / 不做什么"，再展开。
- **MECE**：同层章节不重叠、不遗漏。如"创建/修改/删除优惠券" 不应各自夹带控件细节，否则与"4. UI 交互"重叠。
- **业务与 UI 严格拆分**：
  - 业务规则章节出现"输入框" / "下拉框" / "灰显" / "弹窗" / "placeholder" → 错位，移到 UI。
  - UI 章节出现"长度 [1-50]" / "唯一性校验" / "状态机转移" → 错位，移到业务规则；UI 章节仅引用，例如"长度按业务规则 3.2 校验"。
- **横切关注点独立成章**：操作日志、权限、埋点、跨团队接口、验收 各自一章。**不要散落在功能描述里**（如把"操作日志"塞在《删除优惠券》末尾），那样下游同学（运营、数据、安全）要翻完整篇才能收齐自己关心的内容。
- **DEMO / 线框图** 只放 UI 章节，业务规则章节用文字描述。

## 12 个诊断维度（0 结构合规 + 1-11 内容质量）

读 PRD 时，每一段都自问下列问题。任何一个"否"或"模糊"都是 finding。

### 0. 结构合规（金字塔原则 + 重要程度排序 + 相关聚合）

- [ ] 是否结论先行（每章首段说清范围与边界）？
- [ ] 顶级章节是否按"重要程度递减"排序（需求 → 业务规则 → UI → 运营治理 → 技术对接 → 验收）？
- [ ] 顶级章节数 ≤ 6？相关项是否聚合（如操作日志/权限/统计埋点 → 运营与治理；背景/目标/用户/用例 → 需求概述）？
- [ ] 同层章节是否 MECE（无重叠、无遗漏）？
- [ ] 业务规则与 UI 交互是否在不同章节？业务章节有无渗入 UI 控件？UI 章节有无重复业务校验？
- [ ] 字段定义、校验规则、错误文案 是否合并在同一张字段表里（不要前后散落）？
- [ ] 顶层是否有清晰的"目标 / 非目标 / 成功指标"？还是直接进入功能罗列？

**反例**：
> 《创建优惠券》一节里同时出现"控件类型：下拉框"（UI）、"面额必填、不超过订单金额"（业务）、"错误原因提示"（UI）、"逻辑删除"（业务）、操作日志说明（横切）。
> → 业务/UI/横切 三者混在一起，前端、后端、运营要从同一节里挑各自需要的内容。

---

以下为 1-11 内容质量维度。**逐项详细 checklist + 反例见 `references/dimensions-cheatsheet.md`，扫描时对照打勾；此处仅列维度名与核心问，勿在两处各自展开（防同步漂移）。**

1. **逻辑自洽** —— 前后矛盾？循环定义？默认值与校验冲突？隐含假设（"复用现有优惠券模板"读者找得到文档吗）是否成立？
2. **术语与主语** —— 关键术语首次定义？同概念多名混用？主语显化（"即时生效"谁让它生效）？代词指代清晰？
3. **业务字段完备性（仅业务语义）** —— 查业务含义 / 默认值 / 必填 / 枚举取值 / 创建后可改性 / 是否参与某些计算或规则。**默认不查类型 / 长度 / 存储口径（研发实现，PRD 不写）**；仅当 PRD 是"数据契约"性质（统一业务模型 / 开放平台 API / 跨系统对接）才恢复完整字段查（类型 / 长度 / 枚举 / Nullable / 版本演化）—— 见工作流 step 0 判型。
4. **状态机与生命周期** —— 状态枚举穷举？转移闭环（无"进得去出不来"）？各状态可触发动作？物理 / 逻辑删除 + 历史引用？并发编辑策略（锁 / 后写覆盖 / 冲突提示）？
5. **边界与异常** —— 数量上限有依据 + 超限文案？空态 / 依赖降级 / 越权拦截 / 存量数据迁移？
6. **验收可测性** —— 每点可写 assertion？数值口径（"快"→ ms）/ 时间口径（"即时"→ <1s）量化？SLA 量化？
7. **依赖与复用边界** —— "复用 XX" 划界（哪些复用 / 不复用）？跨团队接口入参 / 出参 / 错误码 / 超时 / 重试 / 兜底约定？"由 XX 决定"的口子位置 + 交付时间？
8. **操作日志（横切，独立成章）** —— 独立章节（散落不算合规）？动作清单全？日志字段全（操作人 / 时间 / 终端 / 动作 / 对象快照 / 变更摘要）？不记录项 + 理由？展示位置 / 保留期 / 改名删除后回溯口径？
9. **权限（横切，独立成章）** —— 独立章节？角色 × 资源 × 动作矩阵全？跨商户/租户隔离？越权文案（统一"无权操作"，不暴露资源）？与现有权限模块衔接？
10. **统计分析与埋点（横切，独立成章）** —— 独立章节？业务指标定义（口径 / 维度 / 公式）？埋点事件清单（事件名 / 时机 / 字段 / 前后端 / 接入方）？看板入口？
11. **表达精准度** —— 模糊量词 / 模糊主语 / 口语化 / 时态模糊 / 长句嵌套 → 量化 / 显化执行方 / 书面化 / 给 milestone / 拆短句或表格化。

## 输出模板

诊断报告以下面这个结构写出来，markdown 格式：

````markdown
# PRD 诊断报告：{PRD 标题}

- 文件：`{path}`
- 扫描时间：{YYYY-MM-DD}
- 总览：P0 {N} / P1 {N} / P2 {N}
- 评审结论：**{可评审 / 建议补充后再评审 / 阻塞评审}**

## 严重度定义
- **P0** 阻塞研发：含矛盾、状态机有断点、关键字段缺失、跨团队接口未约定、章节严重错位。不解决无法估时。
  - 错位判 P0 的界：业务/UI/横切 混在**同一段落或同一表格**里。
- **P1** 影响实现：含术语歧义、校验/默认值缺、异常分支缺、横切关注点散落。研发会反复问 PM。
  - 错位判 P1 的界：横切**已单独成段、但位置靠后或内容不全**（未与功能描述混写）。
- **P2** 表达优化：含口语化、长句、量词模糊。不影响实现，但读起来累。

**评审结论判定**（写报告头 `评审结论` 按此选，勿凭感觉）：
- 任一 P0 → **阻塞评审**
- 无 P0 但 P1 ≥ 3 → **建议补充后再评审**
- 否则 → **可评审**
````

## 写报告时的注意事项

- **引原文一定准确**。不要意译，复制原文。原文超 40 字就截前 40 字加省略号。
- **位置要可定位**。给章节名 / 表格列名 / 锚点都行，最好让 PM 一眼跳到那块。
- **一个 finding 只讲一件事**。不要把多个问题塞一条。
- **改写建议要落地**。说"建议明确" 是废话，要直接给出"明确成什么样"。
- **不要发明事实**。如果某字段类型没说，写 "未指明"，不要替 PM 假设它是 varchar(50)。
- **不要刷数量**。能合的合，能略的略。一份报告 5-30 条比较合理；上百条说明你在凑数。
- **保持中文语境**。技术词允许英文（如 LLM、SLA、CRUD），但行文中文。
- **改写建议保留 PRD 原有语气**。PM 用"复用现有优惠券模板"就别改成"reuse existing coupon template"。

## 何时反问而非直接出报告

- 用户给的是 PRD 草稿大纲（< 50 行），直接出报告意义不大 → 先问"是否要按金字塔骨架 + 12 维度补全"。
- 用户只贴了片段并问"这段怎么样" → 只评这段，别越界审整篇。
- 同时给了多份 PRD → 问优先级，一份一份来，别串。

## 不做的事

- 不直接改写 PRD 文件。报告交付，由 PM 自己决定取舍。
- 不评判产品决策本身（"这个需求该不该做")。只评 PRD 写得清不清楚。
- 不假装懂业务背景。涉及业务结论时引用原文 + 标"待 PM 确认"。
