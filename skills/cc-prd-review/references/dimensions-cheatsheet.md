# 12 维度 Checklist（带反例）

逐项快速扫，命中"否"即记 finding。每条带一个真实反例（来源：内部 PRD 常见坑）。

## 0. 结构合规（金字塔 + 重要程度排序 + 相关聚合）

- [ ] 每章首段结论先行（一句话说清范围 + 边界）
- [ ] 顶级章节按重要程度递减：一、需求概述 → 二、业务规则 → 三、UI 交互 → 四、运营与治理 → 五、技术对接 → 六、验收与上线
- [ ] 顶级章节数 ≤ 6（超 8 说明聚合不够）
- [ ] 同类聚合到位：
  - 操作日志 / 权限 / 统计埋点 合为 「四、运营与治理」 三子节
  - 背景 / 目标 / 用户 / 用例 合为 「一、需求概述」 五子节
  - 跨团队接口契约 / SLA 合为 「五、技术对接」
  - 验收用例 / 灰度 / 数据迁移 合为 「六、验收与上线」
- [ ] 同层章节 MECE（不重叠、不遗漏）
- [ ] **业务规则 与 UI 交互 分章**？业务不出现控件名；UI 不重复业务校验。
- [ ] **运营与治理** 单独成章（即使权限本期不做，也要标注本期不做 + 默认策略）
- [ ] 字段定义 / 校验规则 / 错误文案 合并在同一张字段表（不要前后散落）
- [ ] 顶层有清晰的"目标 / 非目标 / 成功指标"

**反例 A（业务/UI 混杂）**：
> 《创建优惠券》一节同时含「控件类型：下拉框」「面额 [1-1000]」「错误原因提示」「校验规则」「逻辑删除」 → 业务、UI、状态机混在一段，前后端各自挑各自的，容易漏。

**反例 B（横切散落）**：
> 操作日志放在《删除优惠券》末尾，权限只剩"// 暂无"，埋点全文未提。
> → 运营 / 安全 / 数据同学每人翻整篇还找不到自己关心的内容。

## 1. 逻辑自洽

- [ ] 前文表述与后文表述无矛盾
- [ ] 默认值与校验规则一致（默认空 vs 必填）
- [ ] 表格 A 的字段定义与表格 B 的字段定义一致
- [ ] 引用的"复用 XX 模块"在事实层面成立

**反例**：
> 表格 1：「优惠券名称 允许重名，不做唯一性校验」
> 表格 2：「校验规则：唯一性」
> → 直接矛盾。

## 2. 术语与主语

- [ ] 关键术语首次出现时定义
- [ ] 同一概念不混用别名
- [ ] 每个动作句有明确主语
- [ ] "它/该/此"指代清晰

**反例**：
> 「即时生效，仅对线上正式版本起效」
> → 谁让它生效？发布按钮？后端定时任务？

## 3. 业务字段完备性（仅业务语义）

默认**不查**字段类型 / 长度具体上限 / 数据库存储口径 —— 那是研发实现，PRD 不需写。

仅查**业务语义**：

- [ ] 字段名
- [ ] 业务含义（一句话说清它在业务上代表什么）
- [ ] 默认值（业务层面，如"默认停用"）
- [ ] 是否必填（业务层面）
- [ ] 取值范围 / 枚举（业务语义，如"适用范围 = 全部商品 / 指定品类 / 指定商品"）
- [ ] 创建后是否可改？改后走草稿还是即时生效？
- [ ] 是否参与某些计算 / 业务规则（如"备注字段不参与核销规则"）

**反例**（合理的业务字段问题）：
> 「适用范围 | 全部商品 / 指定品类 / 指定商品」
> → "指定品类" 从哪来？复用已有的品类树模块？多选还是单选？有无数量上限（业务层面）？

**不算反例**（属研发实现，不查）：
> 「优惠券名称 长度 1-50」 —— 长度 50 是技术决定还是业务决定？除非业务文档明确"短信限 70 字"这种业务上的硬约束，否则不审。

**例外：数据契约 PRD**。当 PRD 明确是"统一业务模型 / 开放平台 API / 跨系统对接协议"时，恢复完整字段查（类型、长度、枚举值、必填、默认值、Nullable、版本演化）。

## 4. 状态机与生命周期

- [ ] 状态枚举穷举
- [ ] 每个状态可触发的操作列出
- [ ] 状态转移闭环（无"进得去出不来"）
- [ ] 删除是物理 / 逻辑明确
- [ ] 历史引用追溯方式明确
- [ ] 并发编辑策略明确（锁 / 后写覆盖 / 冲突提示）

**反例**：
> 「已下线 + 存在未发布草稿」
> → 已下线后能否重新发布草稿？发布后回到哪个状态？文档没说。

## 5. 边界与异常

- [ ] 数量上限有依据
- [ ] 超限文案明确
- [ ] 空状态展示明确
- [ ] 依赖系统降级行为明确
- [ ] 越权拦截策略明确
- [ ] 存量数据迁移方案明确

**反例**：
> 「默认每个商户最多创建 20 张优惠券」
> → 20 从哪儿来？技术约束还是产品决策？后期能不能调？

## 6. 验收可测性

- [ ] 每个需求点可写成 assertion
- [ ] 数值口径明确（"快" → "P95 < 500ms"）
- [ ] 时间口径明确（"即时" → "事务提交后 < 1s"）
- [ ] 性能 / 容量 SLA 量化

**反例**：
> 「保存后即时生效」
> → 测试同学怎么测？盯着秒表数 1 秒？

## 7. 依赖与复用边界

- [ ] "复用 XX" 的范围划界
- [ ] 跨团队接口入参 / 出参 / 错误码 / 超时 / 重试 约定
- [ ] "由 XX 团队决定" 的口子位置 + 交付时间

**反例**：
> 「最终能否核销由风控侧决定（内部规则本 PRD 不展开）」
> → 风控侧需要 PRD 哪些字段作为输入？什么协议 / 频率 / 失败兜底？

## 8. 操作日志（横切，独立成章）

- [ ] 独立"操作日志"章节存在
- [ ] 记录动作清单完整：创建 / 修改 / 启停 / 发布 / 删除 / 撤回 / 权限变更
- [ ] 日志字段：操作人 / 时间 / 终端或 IP / 动作类型 / 对象快照（名称+版本）/ 变更摘要
- [ ] 不记录动作及理由
- [ ] 展示位置 / 保留期 / 查询入口
- [ ] 改名 / 删除后的回溯口径（快照取值时机）

**反例**：
> 操作日志写在《删除优惠券》后面一段。
> → 运营找不到，安全审计也找不到。横切关注点必须独立成章。

## 9. 权限（横切，独立成章）

- [ ] 独立"权限"章节存在
- [ ] 角色权限矩阵：主账号 / 子账号 / 客服 / 运营 × 资源 × 动作
- [ ] 跨商户 / 跨租户隔离策略
- [ ] 越权拦截行为与文案
- [ ] 与现有权限模块衔接（复用现有角色 or 新增）

**反例**：
> 「权限管理：// 暂无」
> → 即使本期不做也要写清"本期不做 + 默认策略（如仅主账号可操作）+ v2 评估"，不能留白。

## 10. 统计分析与埋点（横切，独立成章）

- [ ] 独立"统计 / 埋点"章节存在
- [ ] 业务指标定义（口径 / 维度 / 计算公式 / 衡量周期）
- [ ] 埋点事件清单（事件名 / 触发时机 / 字段 / 前端or后端 / 接入方）
- [ ] 数据看板入口
- [ ] 与现有看板的整合方式

**反例**：
> 全文未提埋点 / 数据看板。
> → 上线后 PM 想看"优惠券核销率"发现没数据，紧急加埋点。

## 11. 表达精准度

模糊量词 → 量化：

| 模糊词 | 改写方向 |
|---|---|
| 一些、较多、适当 | 给数字或范围 |
| 尽快、稍后、未来 | 给 milestone 或"本期不做" |
| 可能、或许、应该 | 改 must / may / 删除 |
| 大概、估计 | 给依据或承认未知 |

模糊主语 → 显化：

| 模糊主语 | 显化 |
|---|---|
| 即时生效 | "保存按钮点击后，后端 < 1s 内对线上版本生效" |
| 走草稿流程 | "进入草稿状态，发布按钮才会更新线上版本" |

口语化 → 书面：

| 口语 | 书面 |
|---|---|
| 咱们 / 我们 / 大家 | 系统 / 用户 / 运营 |
| 给大家看 / 来看下 | 删除 |
| 比较好 / 还不错 | 删除或量化 |
