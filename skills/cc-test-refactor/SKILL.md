# cc-test-refactor — 测试用例重构（体检式）

对一个业务域的存量测试做体检式重构。核心方法：**先盲设计，后对比**——在看现有测试之前，先独立从业务代码推导出"这个域应该有哪些用例"，再拿现有测试与之对照。先看现有测试会被既有结构锚定：只能挑出小毛病，看不出整块的覆盖缺失和层级错位。

## 触发与输入

- **仅手动触发**（`/cc-test-refactor` 或点名本 skill）。
- 输入：业务域的**关键类**（聚合根 / AppService / DmService 等，类名或全限定名）。没给就反问一次。
- 产出：改进 spec（讨论稿），**全程不改任何代码**。spec 讨论收敛后的执行是后续任务（届时走 testing-guidelines 正常写测试流程）。
- 一次只做一个业务域；用户给多个域时逐个跑完整四阶段。

## Phase 1：读业务代码，建上下文

**本阶段禁止读任何测试代码**——`src/test/` 下一律不碰，包括 `_scaffold`。原因见上：避免被现有用例锚定，这是整个方法的前提。

1. 从用户给的关键类出发，优先用 IntelliJ MCP（`ide_find_class` / `ide_file_structure` / `ide_find_references` / `ide_call_hierarchy`）向外扩读：
   - 聚合根 / 实体：状态字段、状态机、不变式、guard / 校验规则
   - AppService（Cmd / Query）：每个公开方法 = 一个业务入口；参数、归属 / 权限校验、事务边界
   - DmService、Port / Provider：跨域依赖点（即后续的 Fake 边界）
   - 相关 Entity / DDL：持久化形态、唯一约束
2. 输出**业务上下文摘要**：域职责一句话、业务入口清单（方法级）、状态机与关键规则清单、跨域依赖清单。
3. 摘要里有拿不准的业务语义 → 向用户确认后再进 Phase 2；都清楚就直接进。理解错了后面全错，这里是唯一的廉价纠错点。

## Phase 2：盲设计理想用例集

先调 `testing-guidelines` skill（读 `dev-docs/testing-guidelines.md`）。测试类型判定、命名、断言、Mock/Fake、脚手架规则以它为单一来源，本 skill 不复述。

设计原则：

- **从业务规则倒推用例**，不从方法签名正推。每个用例写一栏"业务价值"：它防住什么真实事故（错误放行 / 数据错乱 / 越权 / 状态机非法跳变…）。写不出业务价值的用例不设计——不造空壳。
- **金字塔分层**（判定按规范 1.1–1.5）：纯逻辑 / 状态 / 规则 → SSpec 占大头；持久化、查库、事务、并发 → MSpec 少量兜底；外部系统对接 → IT。同一条规则不在两层重复验证，价值放在能真实验证它的最低层。
- **只测入口**（AppService / DmService），同域底层（Dao / TxService）不单独测、也不 Fake。
- **用例包·用例类组织**：`_feature/<域>/` 下按行为主题拆类（参考现状如 `XxxAggrCrudSSpec` / `XxxAggrPublishSSpec`），一类一个行为主题；脚手架归 `_scaffold/`。

输出**理想用例清单**，按用例类分组：

| 用例类（层级） | context | 用例名 | 业务价值 |
|---|---|---|---|

## Phase 3：读现有测试，双向对比

现在才读该域现有测试（含 `_scaffold`、工厂）。对比是**双向**的，不是给自己的设计找确认：

- **缺口**：理想清单有、现状没有 → 按业务风险排优先级
- **空壳**：无业务价值、验中间态 / 实现细节、与其他用例重复 → 待删 / 待合并
- **层级错位**：该 MSpec 验的写成 SSpec（内存态断不到库）、纯逻辑却起容器 → 待搬层
- **规范违规**：命名、断言、Mock/Fake 用法、数据构造，对照 testing-guidelines 逐条
- **反向吸收**：现有用例覆盖了我没想到的边界 → 承认并并入理想清单，不要为自洽硬说人家多余

## Phase 4：产出改进 spec，讨论

写到 `docs/superpowers/specs/<域>-test-refactor-spec.md`（与 superpowers 产出的 spec 统一归档），结构：

1. 业务上下文摘要（Phase 1 产物浓缩版）
2. 现状总览：现有用例类 / 用例数、按层分布
3. **改进清单**（核心）：每条 = 动作（新增 / 删除 / 改写 / 搬层 / 合并）+ 目标（类·用例）+ 理由（业务价值或规范条款）+ 优先级
4. 保留不动的部分：明确列出，免得讨论时被默认遗漏

发给用户逐条讨论。**讨论收敛前不执行任何代码改动**；用户确认后说"执行"，才按 spec 改造（普通写测试任务，不在本 skill 内）。
