# cc-code-readability — 可读性重构（等价变换）

对**指定文件 / 类**做可读性提升。铁律：**只做行为等价的变换，不改任何业务规则**。
流程是**先出改动清单 → 你勾选批准 → 才动手改 → 编译 + 跑相关测试验证**。不是一上来就改。

这个 skill 的价值不在"知道好代码长啥样"，而在把三件事做扎实：① 一份**保证行为不变的安全改法目录**；② 一份**看着像可读性、实则偷改行为的陷阱清单**；③ 一套**改完能证明没改坏的验证纪律**。

## 触发与输入

- **仅手动触发**（`/cc-code-readability` 或点名本 skill）。
- 输入：一个或几个**文件路径 / 全限定类名**。没给就反问一次，别猜。
- 产出：Phase 2 先给**改动清单（不改代码）**，Phase 3 你批准后才改。
- 一次聚焦一个文件/类；给多个就逐个跑完整流程，别混着改。

## 北极星：只做等价变换

每一条改动都必须**行为等价**——同样的输入产生同样的输出、同样的副作用、同样的异常。判断依据不是"我觉得差不多"，而是能说清"为什么这两段语义相同"。

**拿不准是否等价 → 不改，列进清单标红让人决定。** 宁可少改一条，不可偷偷改坏一条业务规则。这是本 skill 存在的全部前提。

## 与 `cc-code-review` 的分工

`cc-code-review` 审的是**正确性 / 规范**、找 bug，出报告不动手。本 skill 只管**可读性**、且**会动手改**（批准后）。别互相抢：发现真 bug / 逻辑问题 → 记一句提示用户走 `cc-code-review`，本 skill 不顺手"修 bug"，因为修 bug 就是改行为，违背铁律。

命名规范、可空性、`Optional` 用法等 Java 通用约定，以 `java-coding-standards` skill 为准，本 skill 不复述、用到时加载它。注释怎么写以你的既有约定为准（只写 why、不引 spec 编号）。

## Phase 1：定位 + 建测试基线

1. 定位目标：优先 IntelliJ MCP（`ide_find_class` / `ide_read_file` / `ide_file_structure`）读全类。
2. 找**相关测试**：同名 `*Spec.kt`（kotest，本项目主力）/ `*Test.java`，以及直接测这个类的用例。
3. **先跑一次相关测试确认基线是绿的**。基线本来就红 / 没有测试 → 记下来告诉用户：这意味着 Phase 4 的验证能力有限，涉及逻辑的改动风险自负。
   - 跑 kotest 的命令坑参见你的既有约定（`-Dtest='*SSpec'` 通配、需 `-am` 避增量假错）。

基线没建起来（测试跑不起来又不是本次能修的），只做 🟢 级纯机械改动，🟡🟢 以外一律不碰。

## Phase 2：产出改动清单（**不改代码**）

按下面的**安全改法目录**逐类扫，每条改动落到 `file:line`，按风险分级。用这个格式：

```
## 可读性改动清单：{文件/类}

基线：相关测试 {N} 个，{全绿 / 红 X 个 / 无测试}

| # | 位置 | 类型 | 现状 → 改法 | 风险 |
|---|---|---|---|---|
| 1 | Foo.java:42 | 重命名 | `a` → `subUserId` | 🟢 |
| 2 | Foo.java:88 | 卫语句 | 3 层嵌套 if → 早返回 | 🟡 |
| 3 | Foo.java:120 | 条件化简 | `!(a && b)` → `!a \|\| !b` | 🔴 短路副作用存疑 |
```

风险分级（决定改法与验证强度）：

- **🟢 纯机械等价**：格式、import、IDE 重命名、删死代码/未用变量、魔法值提常量。编译过即可。
- **🟡 手改但逻辑无关**：抽变量、抽纯计算方法、卫语句拍平嵌套、缩小作用域、删噪音注释。编译 + 跑相关测试。
- **🔴 碰语义边界**：条件/布尔化简、`Optional`/stream 链改写、异常流调整、任何涉及求值顺序/副作用的。**默认不改**，列出疑点让用户决定；批准才改，且必跑测试。

清单末尾一句总结：🟢 X 条 / 🟡 Y 条 / 🔴 Z 条，等你勾选。**本阶段结束前不碰任何代码。**

## Phase 3：等批准

用户回"全改 / 改 1,2,5 / 跳过 3"等。没明确批准 → 不改。🔴 条目除非用户逐条点名同意，否则不动。

## Phase 4：应用 + 验证

- **能走 IDE 语义重构就走**：重命名用 `ide_refactor_rename`、删代码用 `ide_refactor_safe_delete`、格式用 `ide_reformat_code`、import 用 `ide_optimize_imports`——这些天然等价，改所有引用不漏。
- 手改的部分改完：`ide_diagnostics` / `ide_build_project` 保证编译；🟡🔴 条目跑 Phase 1 那批相关测试。
- 报告结果：每条标 `✅ 已改`，附编译/测试结论（`测试 N 个全绿`）。测试没过 → **回滚这条**，说明原因，绝不带着红测试收工。
- 全程不动 Maven module / dependency（项目铁律），可读性改动本就不该碰依赖。

## 安全改法目录

| 改法 | 说明 | 落地方式 |
|---|---|---|
| 重命名 | 变量/方法/参数改成意图清晰的名 | `ide_refactor_rename`（语义级，自动改引用） |
| 死代码清理 | 未用变量、注释掉的代码、不可达分支 | `ide_refactor_safe_delete`（先查引用） |
| 抽取变量 | 给 magic 子表达式命名 | 手改 |
| 抽取方法 | 拆长方法，**只拆纯计算 / 无副作用块** | IDE extract 或手改 |
| 卫语句 / 早返回 | 拍平嵌套 if（箭头代码） | 手改，盯异常流与 return 时机 |
| 魔法值 → 命名常量 | `3` / `"AI_AGENT"` 提成常量 | 手改 |
| 缩小作用域 | 声明挪到就近使用、收窄可见性 | 手改，注意 JPA/序列化字段别动 |
| 布尔 / 条件化简 | 去双重否定、德摩根 | 🔴 手改，盯短路语义 |
| 注释 | 删噪音注释（判定见下节）；**不代笔 why 注释** | 依既有注释约定 |
| 格式 / import | 交给工具，不手动 | `ide_reformat_code` / `ide_optimize_imports` |

## 噪音注释判定

"删噪音注释"要有边界，否则 LLM 要么不敢删，要么把有用的信息删掉。**注释删了 git 找得回，但没人会去找——按不可逆对待。**

**总判据：这条注释是否携带了从代码 + 团队共识里读不出的信息。** 读得出 → 噪音。
真 why 携带的是**外部事实**：DB 列宽 / NOT NULL 约束、唯一索引名、库的版本限制、上游系统的坑、实测数字——这类东西没人告诉你就是不知道。
而"这个工具好用在哪""这里做了个决策"不算：那是共识，不是信息。
判不准时问一句：**一年后第一次读这段代码的人，会不会因为少了这句而卡住？** 不会 → 噪音。

**可删（归 🟡，判定明确的按 🟢）**

- **复述代码**：`// 设置用户名` 压在 `user.setName(name)` 上。
- **变更日志 / 施工痕迹**：`// 2026-08-12 张三修改`、`// 本次需求新增字段`、`// 原来逻辑有问题改成这样`。这是 git blame 的活。
  **隐蔽形式**：不带"原来 / 本次"字样、实质却在论证"这次为什么从 A 改成 B"的注释。读者看到的只有改完的代码、没有 A，注释就退化成论证一个显然的选择。
- **注释掉的死代码**：整段被注掉的调用 / 分支。
- **模板噪音**：只有 `@param name the name` 的自动生成 Javadoc、`// ===== getter/setter =====`、`// 构造函数`。
- **显然常识**：`i++; // i 加 1`、`private static final int MAX = 100; // 最大值 100`。
- **靠改名就能消除的**：`int d; // 距离，单位米` → 重命名 `distanceInMeters`，注释一并删（一条改动，别拆两条）。
- **解释工具 / 库通用价值的**：`// 用 EasyRandom 打底，避免实体新增 NOT NULL 列时又要回来补字段` 压在 `defaultValueEasyRandom.nextObject(X.class)` 上；同类还有 `// 用 Optional 避免 NPE`、`// 用 Streams2 简化遍历`。
  工具存在的理由是团队共识，在几十个调用点各重复一遍就是噪音——**判据：同一个工具在本 codebase 被用了几十次，只有这一两处加了说明，那这说明多半解释的是工具、不是这一处。**
  真正值得注释的是这一处**反直觉**的地方（为什么单单这个字段要手工覆盖、为什么这里必须绕开工具）。

**必须留（哪怕看着像废话）**

- 解释 **why** 的：为什么是这个数、为什么不用显然写法、业务 / 风控约束、外部系统的坑。
  **限定**：why 必须落在**这一处**的特殊性上。解释通用写法 / 工具好处的，归上面"可删"，别拿"这也是 why"糊过去。
- `TODO` / `FIXME` / `HACK` / `XXX`——待办账本，不是噪音。
- `@Deprecated` 的替代说明、`@SuppressWarnings` 的抑制理由。
- **public API / 对外 SDK 的 Javadoc**——字段级看着重复，但它是 IDE 提示和文档产出。
- **看不懂在说什么的**：看不懂 ≠ 没意义，可能是你不知道的历史坑。列出来问，别删。
- **和代码对不上的注释**：不删也不改，列 🔴。代码和注释必有一个是错的，判断哪个错属于 `cc-code-review`，本 skill 无权定夺。

**不代笔 why 注释**

安全改法目录里的"补 why"只限**能从代码本身确凿读出**的情况（例：魔法值提常量时，把它的出处写进常量名）。**业务动机你不知道，编一条比没有更糟**——一条编造的 why 会被后来者当事实信。该补 why 的地方列进清单标一句"此处缺 why，建议作者补"，不要代笔。

## 陷阱清单（看着无害，实则改行为——重点防这些）

LLM 最容易在这里把可读性改成 bug。命中任一条 → 归 🔴，默认不改：

- 调换 `&&` / `||` 两侧 → 短路副作用 / 求值顺序变了。
- `if/else` 改三元，把原本不执行的分支变成**总求值**（含抛异常 / 有副作用的调用）。
- `==` 当 `.equals`、或反过来（尤其包装类型、字符串）。
- "简化"掉一个其实有副作用的调用（日志、缓存写入、懒加载触发、计数）。
- 抽方法时改了**异常传播时机**或 `return` 早退的位置。
- 改 `Optional` / stream 链时改变了 **null vs 空集合**、或改变了终止/惰性求值语义。
- 动了并发相关：`volatile`、`synchronized` 范围、发布可见性、执行顺序。
- 改了 JPA `@Entity` 字段可见性 / 名字、序列化字段、DTO 对外字段 → 影响持久化 / 接口契约。
- 把 `finally` / try-with-resources 的资源释放"简化"没了。
- 重命名跨越了反射 / 配置 / SpEL / MyBatis XML / 前端约定的字符串引用（IDE rename 可能扫不到）。

## 不做的事

- **不改业务规则**。只做等价变换；拿不准就不改、列红条。
- **不顺手修 bug**。发现 bug 提示用户走 `cc-code-review`，本 skill 不动。
- **不批准就不改**。Phase 2 只出清单，Phase 3 拿到明确批准才进 Phase 4。
- **不动依赖 / 结构**：不改 Maven module、dependency、包结构、模块依赖方向。
- **不带红测试收工**。某条改完测试挂 → 回滚那条并说明。
- **不刷数量**。一个文件几条到十几条合理；把无所谓的空格、可有可无的重命名凑成几十条，是噪音。挑真正提升可读性的。

## 何时反问

- 没给目标、或目标含糊定位不到 → 问清哪个文件/类再动。
- 目标是纯配置 / 前端 / 生成代码 → 提醒本 skill 主管后端 Java/Kotlin 手写代码，确认是否继续。
- 相关测试跑不起来且非本次能修 → 告知只做 🟢 级改动，问是否接受。
- 发现改动会牵动接口契约 / 持久化 / 跨模块引用（🔴 且影响面大）→ 单独拎出来问，别混在批量里默认改。
